## 1. 电梯稿（三个版本，直接背）

**30 秒（自我介绍里带一句）**
> 我做过一个自己能天天用的求职 Agent：用一句自然语言描述目标，它自动搜索岗位、读 JD 打分、在明确规则内主动联系招聘者，每天下班前给我一份求职执行日报。核心设计不是"让 AI 全自动"，而是把**判断、执行、授权**拆成三层——LLM 决定做什么，确定性代码决定怎么做，规则决定允不允许。

**90 秒（项目介绍标准版）**
> 求职时我遇到三个问题：每天重复找岗位、判断标准不稳定、投完就没记录。市面上的工具要么是"固定关键词批量投"的脚本，要么是"你自己去点"的推荐列表。
> 我做的是一个在**自己已登录的浏览器**里运行的 Agent：目标 → 规划搜索方向 → 硬过滤 → 读 JD 打分 → 评估候选够不够 → 不够就**限量**补充搜索 → 进入 Policy 决策 → 再由 Agent 联系招聘者或交给我确认。
> 最关键的产品决策是**把"能不能发"从模型手里拿走**：模型只输出结构化判断（计划、分数、新搜索词），能不能发消息由 12 条策略条件决定，而且默认模式（Review）必须我确认，切到自动模式要单独授权、有每日上限和工作时间窗。
> 结果是：我现在能每天让它在规则内跑完一轮，并且**每个岗位最多联系一次**，下班看日报就知道"今天怎么找的、为什么停、还剩哪些好岗位"。

**3 分钟**：用 §4 的 90 秒版接 §5 的三段转折（下面）。

## 4. 90 秒故事（STAR-lite，面试标准用法）

**S（背景）**：我在找工作，每天要重复"搜岗位 → 读 JD → 判断合不合适 → 打招呼"，判断标准还飘（同一类岗位今天觉得合适、明天就跳过）。
**T（任务/我的目标）**：我想让它变成**一套可复用的流程**：稳定的判断标准 + 有边界地替我执行 + 有记录可复盘。我知道"全自动投递"是危险的（发错消息不可逆、平台会风控），所以我把目标定成**"可审计的有界自动化"**。
**A（我做了什么）**：
1. **把能力拆开**：LLM 只做三个无状态判断（规划搜索方向 / 打分 / 候选不足时补搜索词），绝不产生动作；
2. **把执行交给确定性代码**：所有页面动作都是可测的普通代码，模型碰不到 DOM；
3. **把"允不允许"抽成策略层**：12 条前置条件（模式、授权、话术、暂停、工作时间、分数阈值、硬约束、是否联系过、每日上限、信息完整性、验证码、页面健康），**创建动作前和执行前各判一次**；
4. **把事实落成事件**：每个决策写事件（含被拒原因、补搜决策、停止原因），日报完全由事件聚合，不靠 LLM 编。
**R（结果）**：我现在能每天让它在规则内跑完，每个岗位最多联系一次；面板上能看到"为什么继续搜 / 为什么停 / 还剩哪些好岗位"；MV3 后台被回收、侧边栏关掉都不丢进度。
**L（反思）**：**Agent 产品的核心不是"能做多少"，而是"什么时候不做"。** 我把最多的设计时间花在"退出条件"上：什么时候停搜、什么时候不发、什么时候必须交回给人。

## 5. 三分钟故事：三个转折（面试官最爱听的"你怎么做的判断"）

### 转折一：从"全自动"改成"默认人在环"
- **我最初的直觉**：既然叫 Agent，就该尽量自动，用户少动手。
- **推翻了什么**：我列了一张"动作不可逆性"表——搜索/打分可逆（大不了重来），**给真人发消息不可逆**（可能打扰 HR、影响后续机会、甚至触发平台风控）。
- **决策**：不可逆动作默认必须人工确认（Review 模式）；自动模式（Autopilot）**单独授权**，授权页必须展示"将自动发送的完整话术"，且随时可暂停、可撤销。
- **结果**：产品从"我不敢用"变成"我每天在用"。

### 转折二：发现"AI 推荐"和"有权联系"是两件事
- **现象**：我自己跑的时候，面板显示"推荐 12 个"，但自动联系数是 0，我第一反应是"bug"。
- **定位**：这两个数字含义不同——推荐线是"AI 觉得值得关注（≥75 分）"，而自动联系还要求达到我设的阈值（85）、没命中硬约束、没联系过、信息完整、话术有效。
- **洞察**：**这不是 bug，是产品语言的问题**。用户会把"推荐"理解成"你要投的"，于是看到 0 就以为系统坏了。
- **决策**：把概念在界面上显式拆开并命名——`Recommended` / `Autopilot Eligible` / `Round Target` 三个数字同时展示，每次决策都写一行"为什么继续搜 / 为什么停"。
- **结果**：同一份数据，从"看起来像坏了"变成"我一眼知道它为什么这么做"。

### 转折三：把"重复打扰真人"做成机制不可能，而不是靠小心
- **风险**：后台被浏览器回收、侧边栏被关掉、页面刷新……都可能让"发消息"这个动作执行两次。
- **决策**：四道闸门 —— ① 创建动作前查重（队列状态 + 事件 + 历史）；② 执行前再查一次；③ 写入事件时用幂等键；④ 如果发送中途被打断（无法确认是否已发出），标记为**需人工确认**，**绝不自动重发**。
- **结果**："每个岗位最多联系一次"变成**系统保证**，而不是"我操作小心"。

## 7. 关键产品决策卡（九张，面试时按需抽用）

### D1 为什么做 Agent，而不是脚本或爬虫？
- **背景**：同类工具多是"关键词 + 固定流程批量投"。
- **选项**：（a）固定关键词脚本；（b）纯规则推荐列表（用户自己投）；（c）目标驱动 Agent。
- **决策**：（c），但**只让模型做判断，不让它做动作**。
- **依据**：岗位匹配需要理解语义（JD 与个人画像的匹配没有关键词能穷举），但"发消息"必须可预测、可测试、可撤回。
- **代价**：需要额外做一层结构化契约（模型只输出 JSON、程序校验），开发量更大。
- **一句话**：**"用模型做判断，用代码做动作——这是这个项目最重要的分工。"**

### D2 自主权怎么给？（默认 Review，Autopilot 要授权）
- **依据**：按"动作不可逆性"分配自主权；不可逆动作默认人工确认。
- **补充**：自动模式有 6 个硬边界（分数阈值 / 每日上限 / 候选目标 / 最大轮次 / 工作时间窗 / 风险即停）。
- **代价**：自动化程度看起来"不够激进"。
- **一句话**：**"我宁愿它少做，也不愿它做错——所以我给的是有界自主权。"**

### D3 为什么要有"每日上限"和"候选目标"两个数字？
- **背景**：两者都像"额度"，容易被当成一个。
- **决策**：拆成两个语义 —— **候选目标**决定"这轮凑够几个就停止继续搜"（探索的停止条件），**每日上限**决定"今天最多联系几个"（外发动作的硬上限）。
- **依据**：这两个约束优化的是不同的东西——前者是成本与效率，后者是风险与体验。
- **代价**：设置项变多，需要更清楚的文案。
- **一句话**：**"一个控制我花多少力气去找，一个控制它最多替我打扰几个人。"**

### D4 工作时间窗与"到点收工"
- **决策**：只在设定时间窗内搜索与联系；超窗立即收工，不为凑额度继续跑；如果离结束不到 15 分钟就启动，会提醒"本轮可能跑不完"。
- **依据**：不要在夜里给 HR 发消息（体验与合规）；也不要给用户"它偷偷在干活"的失控感。
- **一句话**：**"自动化必须让人知道它在什么时候干活。"**

### D5 日报里为什么不显示"HR 回复 0 / 简历 0 / 面试 0"？
- **背景**：日报模板里很容易加上这些字段，显示 0 看起来"完整"。
- **决策**：**不显示**。改成在日报里单列一节"尚未监测"：本版本没有对话监测能力。
- **依据**：**0 不是事实**——它会让用户误以为"今天没人回我"，而真相是"系统还没能力看"。
- **一句话**：**"能力缺失要如实说，不能用一个 0 掩盖。"**（这条最能体现产品人的诚实与边界感）

### D6 为什么用"事件 + 状态"两层，而不是一张表？
- **决策**：所有发生过的事写成只追加的**事件**（不可改），当前状态由事件派生并单独保存；日报完全由事件聚合。
- **依据**：用户要能回答"为什么发/为什么停"，就必须有不可篡改的事实层；而界面需要的是"现在是什么状态"，两者职责不同。
- **代价**：实现复杂度上升（需要处理重复、保留期、状态一致性）。
- **一句话**：**"审计能力和展示能力分开设计，日报才敢说是'数据'而不是'总结'。"**

### D7 提前收敛：为什么不是"找得越多越好"？
- **现象**：早期版本一轮要抓 15 个岗位详情、评 3 批分，才判断"够不够联系"。
- **决策**：详情数量随候选目标缩放（目标 2 个 → 只抓 6 个），并且**边抓边评**，一旦凑够候选目标就立即停止抓取与评分。
- **依据**：每多抓一个岗位都是一次真实页面访问与一次模型调用——**成本意识也是产品设计**。
- **一句话**：**"判断够不够，比继续找更重要。"**

### D8 搜索词由模型生成，但为什么看起来"总是那几个"？
- **事实**：搜索方向由模型根据目标生成（不是写死的词表）；但为了让结果可复现，模型调用使用确定性解码（`temperature: 0`），同一句目标会得到很接近的词表。
- **我怎么看这件事**：**可复现性 vs 探索多样性是一个显式取舍**——我选择先要可复现（能复盘、能回归测试），把"多样性"交给第二轮补充搜索与用户把目标写得更具体。
- **一句话**：**"我知道它的天花板在哪，也知道下一步该往哪改。"**（面试官问"你的方案有什么不足"时直接用这条）

### D9 成本控制：模型调用怎么不乱花？
- **决策**：只对"还没打过分"的岗位调用模型；打分分批（每批 5 个）并在每批后落盘；失败或恢复后不重复付费。
- **依据**：后台随时可能被回收，"一次调用尽量短、进度随时可续"是可靠性与成本的共同要求。
- **一句话**：**"把不确定性当成默认条件来设计。"**

## 8. 用 PM 语言讲 Agent 概念（面试官可能是非技术背景）

| 概念 | 一句话解释 | 我在项目里怎么做 |
|---|---|---|
| **自主性分级** | 自动化不是一个开关，而是一条滑尺 | 只读（搜索/打分，默认允许）→ 建议（推荐，默认允许）→ **不可逆动作（发消息，默认需确认）** |
| **人在环（HITL）** | 让人的判断出现在"最贵的那一步"之前 | Review 二次确认页会展示将发送的完整话术 |
| **授权（Consent）** | "持续同意"和"这次同意"要分开 | 切到自动模式必须过授权页，并展示将自动发出的完整话术；切回即撤销 |
| **策略门禁（Policy）** | 谁能发，不归模型管 | 12 条条件，创建前 + 执行前各判一次；不通过就不发，并记录原因 |
| **有界执行** | 不做"永远在跑"的东西 | 每次唤醒最多推进 3 步，每步落盘；浏览器关掉就停 |
| **可观测性** | 用户能回答"它为什么这么做" | 面板显示三个关键数字 + 每步决策原因 + 停止原因（人话） |
| **幂等** | 同一次动作重复执行，效果不叠加 | "每个岗位最多联系一次"由机制保证 |
| **成本** | 每次调用都要花真钱 | 候选够就停搜；只对没打分的调用模型；分批落盘避免重试浪费 |

**面试可以直接说的一句**：
> "做 Agent 产品，我把 70% 的设计时间花在**边界**上——什么时候停、什么时候不发、什么时候必须交回给人；剩下 30% 才在'怎么让它做得更多'。"

## 9. 指标体系（这是 PM 面试的必答题，务必诚实）

### 9.1 我会怎么定义这个产品的成功

| 层级 | 指标 | 为什么 |
|---|---|---|
| **北极星** | 每天"值得投的岗位"被有效覆盖的比例（高质量候选 / 全部高质量候选） | 用户要的是"别漏掉值得投的"，不是"投得多" |
| **过程** | 单轮发现数 → 分析数 → 候选数 → 联系数（漏斗）；每轮耗时；停止原因分布 | 判断卡在哪一环：是搜不到、评不准，还是额度/时间先到 |
| **风险/安全** | 误发率（发了不该发的）；重复联系次数（必须为 0）；被平台提示风险的次数 | 这是这个品类的生死线 |
| **效率** | 每个岗位的端到端耗时（人工 vs Agent）；每日日报阅读率 | 证明"省时间"这件事 |
| **反指标** | 只盯"联系数量"会让产品走向刷量 → 所以我把"联系数"降级为过程指标 | 防止指标反过来伤害用户 |

### 9.2 现状：哪些数已可信，哪些还没有（必须主动说）

| 状态 | 说明 |
|---|---|
| ✅ **已可测量** | 因为所有事实都落事件，漏斗、每轮表现、停止原因分布、重复联系次数（应为 0）**都能直接从数据算出来**；我也用真实运行发现并修掉了多个问题（见 §10） |
| ⚠️ **未做对照测量** | 只有我一个用户（自己天天用 = 狗粮测试），**没有做过"手动 vs Agent"的对照实验**，所以我不会说"效率提升 X%"这种话 |
| ❌ **暂时无法测量** | HR 回复率 / 面试转化——因为还没有对话监测能力（这也是为什么日报里不写这些数字） |

### 9.3 如果有人问"你怎么验证价值"，给这个实验设计（显专业）

> 两周对照实验：单周奇偶日交替（手动 / Agent 交替），同一目标、同一时间段。
> - **主指标**：每获得 1 个"我愿意投"的岗位所耗时间（人工：从打开 BOSS 到发出打招呼的时间戳差；Agent：从启动到首次联系的耗时 + 我的确认时间）
> - **质量指标**：我事后标记的"事后愿意继续聊"的比例
> - **安全指标**：误发数（目标 0）、重复联系数（目标 0）
> - 样本量：≥30 个岗位/组，用配对比较；同时记录我对推荐的"心智负担"（每天确认耗时）
>
> 明确说一句：**"这套指标我设计好了，但还没跑完；我不会拿没测过的数字当结论。"**

## 11. 竞品与替代方案（被问"和现有方案有什么不同"）

| 方案 | 它解决什么 | 它的短板 | 我的差异 |
|---|---|---|---|
| 手动投递 | 完全可控 | 重复劳动、标准不稳、无记录 | 判断标准化 + 执行自动化 + 日报可复盘 |
| 平台自带推荐 | 数据最全 | 只在平台内、不按我的标准排序、不替我执行 | 以**我的画像与约束**为准，且能执行 |

| 通用浏览器 Agent（点哪算哪） | 灵活 | 不可预测、难测试、高风险动作无法约束 | **执行路径确定**（不猜页面）、高风险动作有门禁 |

**一句话定位**：
> "别人做的是'投得更多'，我做的是'**投得对、且能停下来**'——因为求职场景里，错误的动作比漏掉的动作贵得多。"

## 12. 边界与伦理（主动讲，这是加分项）

**我不做什么（写在产品原则里）**：
- 不绕过验证码、不做反检测 / 指纹伪装、不用代理池、不做多账号；
- 不自动回复 HR、不自动发简历（本版本无此能力）、不做 HR 自动聊天；
- 不在工作时间之外偷偷联系；
- 不把还没监测到的数据（HR 回复 / 简历 / 面试）写成 0 来"凑完整"。

**为什么这是产品优势**：
1. 求职是低频高价值场景，**一次误发的代价远大于少投十个**；
2. 平台风控是真实约束，绕过它等于把风险转嫁给用户；
3. 用户只有"知道它什么时候会动手、动手前我能拦一下"，才敢长期开着它。

## 13. 二十个刁钻问题 + 参考答法

### A 类：产品判断

1. **"这不就是个爬虫/脚本吗？"**
   > 脚本的执行路径是写死的，我的是"根据结果决定下一步"：搜完发现候选不够会自己补搜索方向，够了就停。更重要的是，脚本没有"能不能做"的判断层——它只会执行；我这里有 12 条策略条件决定"允不允许发"。
2. **"为什么不做成全自动，用户不就想省事吗？"**
   > 选自动模式的用户确实存在，我给了，但要求单独授权、并且有 6 个硬上限。默认模式保留人工确认，是因为"发错消息"不可逆——**省事不能以牺牲退路为代价**。
3. **"你的用户是谁？"**
   > 现阶段用户就是我自己（每天在用），目标用户是**有明确求职方向的互联网从业者**：他们会写目标、会看数据、也关心账号安全。
4. **"没有用户数据，怎么证明价值？"**
   > 我不会假装有。已经能证明的是：（a）功能闭环真实跑通（真实平台 + 真实打招呼）；（b）所有过程数据可查，重复联系数为 0、停止原因可解释；（c）**狗粮测试暴露了 6 个真实问题并都已修复**——这本身就是最有效的早期验证。规模验证实验我已经设计好（§9.3），缺的是样本。
5. **"如果用户目标写得很模糊怎么办？"**
   > 目标模糊会被解析成更宽的搜索方向，同时我会把解析结果**回显**给用户看（目标摘要 + 搜索方向列表），用户可以立刻纠正。产品上不做"猜"，做"给你看我怎么理解的"。
6. **"你怎么防止它投错岗位？"**
   > 三层：硬约束（用户明确否定的词，命中直接排除）→ 分数阈值 → 策略条件；而且默认模式最终还要用户点一下。

### B 类：技术与实现取舍

7. **"为什么要做事件记录，直接写日志不行吗？"**
   > 日记要能回答"为什么"，就必须有不可篡改的事实层。日志是给人看的文本，事件是给系统算的数据——我的日报完全由事件聚合，不解析日志、也不让 LLM 编。
8. **"后台被浏览器回收怎么办？"**
   > 每次只推进一步就落盘，恢复后从断点继续；如果中断发生在"发消息"过程中（无法确认是否发出），就标记成"需人工确认"，绝不自动重发。
9. **"怎么保证不重复联系同一个人？"**
   > 四道闸门（创建前查重 / 执行前再查 / 写入幂等 / 中断保守）。而且"已联系"这个事实在数据清理时**刻意不删**——因为删了就可能重复打扰真人。
10. **"为什么不用现成的 Agent 框架？"**
    > 我的瓶颈不在"编排框架"，而在**执行环境的约束**（浏览器后台随时被回收、页面操作不可并行、外部动作不可逆）。这些框架解决不了我的核心问题，反而增加不可控面。我用依赖注入把可测试性做到位（529 个测试全绿），这比引框架更值。
11. **"模型胡说八道怎么办？"**
    > 三个限制：只输出结构化字段（格式不对直接判失败，不猜）；模型的输出只能影响"候选与排序"，不能产生动作；最后还有规则层与用户确认。
12. **"你做了几个 Agent？"**
    > 一个。三个模型角色（规划 / 补搜 / 打分）都是**无状态、没有自主权、彼此不通信**的判断函数，真正的编排是一个确定的步骤机。多 Agent 在我这个场景只会让"为什么发这条"更难解释。

### C 类：AI 认知

13. **"什么是 Agent？你的定义。"**
    > 我的定义是：**能根据环境反馈自主决定下一步、并且能执行的外部系统**。按这个定义，我做的关键不是"加个 LLM"，而是补上"反馈 → 决策 → 执行"的闭环（搜索结果是反馈，策略判断是决策，打招呼是执行）。
14. **"自主性和可控性冲突吗？"**
    > 冲突的是"**没有边界的自主性**"。我的做法是把自主性分级：读操作放开、写操作收紧；再给写操作加硬上限和随时暂停，冲突就变成了设计参数。
15. **"Prompt 工程在这个项目里占多大比重？"**
    > 占比不大但很关键：三个角色的输出都要能被程序消费（严格 JSON + 字段校验），而且要把"用户目标里的否定词"这类边界情况讲清楚。真正的工程量在"如何让模型的输出不影响安全边界"。
16. **"你的 Agent 会学习吗？"**
    > 现在不会，这是有意的。我做的是"可解释优先"：先保证每个判断都能追溯到事实。偏好记忆与结果反馈学习在路线图里，但要以不牺牲可解释性为前提。

### D 类：风险、伦理与商业

17. **"平台封号怎么办？"**
    > 我把它当产品约束：不做绕过、限制频次、只在工作时间跑、遇到风险页面立即停并交还给人。用户协议里写明风险自担——**但我不会用"反检测"去替用户承担本该公司承担的风险**。
18. **"这东西能商业化吗？"**
    > 直接的"全自动代投"我不看好（风险高、信任难建立）。更可能的方向是**求职过程管理**：判断标准化 + 过程可视化 + 日报复盘；自动化只是其中一环，而且必须可关。
19. **"如果用户用它去骗面试机会？"**
    > 它只做"表达兴趣"这一步，不代替用户面试或伪造经历；所有内容都由用户授权（话术是他自己写的，授权页会展示原文）。产品层面我不提供"批量海投"的能力。
20. **"你觉得这个项目最大的不足？"**
    > 三点：一是**没有真实用户规模验证**（只有我自己）；二是**搜索方向的多样性受可复现性设计限制**（同一目标词表趋同）；三是**节奏偏慢**（受浏览器后台调度与页面访问延迟约束）。三点我都有明确的改进路径（§14）。

## 14. 如果给我团队和三个月（展示优先级判断）

| 优先级 | 做什么 | 为什么先做它 | 怎么衡量 |
|---|---|---|---|
| P0 | **验证实验**：10–20 位真实用户，跑两周对照实验（§9.3） | 没有数据就没有取舍依据 | 每岗位耗时、事后愿意继续聊的比例、误发/重复联系（必须 0） |
| P0 | **提升确定性**：真实使用中的失败原因归类 + 提高成功率 | 自动模式的价值完全取决于"能不能稳定跑完" | 单轮完成率、失败原因分布 |
| P1 | **搜索多样性**：让不同目标/轮次产生真正不同的方向（D8） | 覆盖度直接决定"会不会漏掉好岗位" | 每日新增候选数、跨轮重复率 |
| P1 | **候选池跨天**：今天没联系的优质候选，明天继续处理 | 用户最强的诉求是"别漏" | 优质候选覆盖率 |
| P2 | **对话监测（只读）**：先能"看见"HR 回复并提醒我 | 这是"识别 HR 回复"的前置能力，且风险低（只读） | 提醒准确率/漏报率 |
| P2 | **日报邮件化**：把复盘变成被动接收 | 提升留存（每天必然看到一次） | 日报打开/阅读率 |
| P3 | **简历请求的双确认门**（规则 + 模型双判 + 高阈值） | 高风险动作，必须等前面验证充分 | 误发率（目标 0） |

**讲优先级时的关键句**：
> "先做'能稳定跑完'和'能被验证'，再做'做更多'。高风险动作永远排在验证充分之后。"
